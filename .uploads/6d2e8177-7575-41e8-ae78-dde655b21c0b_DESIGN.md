# dsh-wiring 设计说明

> 把 DeepSeek Harness 官方**已发布但没有任何 profile 挂载**的能力接上线，并让失败可解释。
> 版本：v1 设计（2026-11-12）｜状态：待实现

---

## 1. 命名

| 对象 | 名称 | 理由 |
|---|---|---|
| GitHub 仓库 | `dsh-wiring` | 机制名而非能力名，可扩展；`dsh-awakening` 已被开机动画占用 |
| npm 包 | `@<your-name>/dsh-wiring`（单包） | 一次安装接管全部休眠能力 |
| Loader 行 id | `wiring-lsp`、`wiring-lsp-typescript`、`wiring-lsp-tool`、`wiring-doctor` | `wiring-` 前缀避免与社区 patch 撞 id |
| 工具名 | `lsp_status`、`browser_status`… | `<capability>_status`；每个能力一个，避免重名 |
| 一句话 | **Wire what ships. Diagnose what doesn't.** | 中：接上已发布的，解释没接上的 |

**为什么是单包而不是 core + 每能力一包**：多包意味着跨包依赖，而 profile 安装走 pnpm 的 `file:`/软链解析——这是本项目最可能翻车的地方（provider 的 peer、core 的链接、发布后的 `file:` 失效）。单包把安装面压到最小：一个目录、一次安装、零运行时依赖。**扩展性由 `src/capabilities/` 模块承担，而不是由包边界承担**；等某个能力确实需要独立发版（例如需要平台专属依赖），再拆包，拆除成本很低。

## 2. 设计目标（按优先级）

| # | 目标 | 可验证含义 |
|---|---|---|
| 1 | **不破坏宿主** | `apply()` 不抛、不做 IO、不写 profile；任何探测失败只产出报告 |
| 2 | **失败可解释** | 每条失败都给「装什么、跑什么」，模型与人都能直接执行 |
| 3 | **零依赖零构建** | 无运行时依赖、不 import `@deepseek-ai/*`、无编译；`node` 直接加载 |
| 4 | **扩展零成本** | 加能力 = 1 个模块 + 几行 patch，引擎不改 |
| 5 | **可验收** | 静态检查 + 单测 + 安装后 8 步清单，全部命令化 |

**非目标**：UI、配置写回、自动安装语言服务器/浏览器、内置 provider、遥测。

## 3. 三层架构（单包内）

```
┌────────────────────────────────────────────────────────────────┐
│ L1 声明层  cordis.patch.yml                                     │
│    seam 行 → provider 行（每实例一行）→ tool 行 → doctor 行      │
│    无逻辑、无 !!js、不覆盖用户行                                  │
├────────────────────────────────────────────────────────────────┤
│ L2 引擎层  src/index.js（~130 行，零依赖）                       │
│    runChecks / defineStatusTool / formatReport                  │
│    纯函数 + 每检查有界超时 + 全量 catch → 永远返回报告            │
├────────────────────────────────────────────────────────────────┤
│ L3 能力层  src/capabilities/<id>.js（每个 ~60 行）               │
│    capability 描述符 + checks 表                                 │
└────────────────────────────────────────────────────────────────┘
```

依赖方向：能力模块 → 引擎。引擎不认识任何具体能力，启动时遍历 `capabilities` 注册工具。宿主只通过注入的服务访问：`subprocess`、`tools`、`ctx.get(name)`。

## 4. 契约

### 4.1 Check

```js
/**
 * @typedef {object} Check
 * @property {string} id        稳定 id，报告键
 * @property {string} label     人读标签
 * @property {'command'|'path'|'service'} kind
 * @property {string} [command] kind=command：交给 ctx.subprocess.resolveExecutable 解析
 * @property {string} [path]    kind=path：绝对路径存在性
 * @property {string} [service] kind=service：ctx.get(service) 是否存在
 * @property {string} [install] 可直接复制执行的安装命令
 * @property {string} [hint]    其他可执行建议（如 npx playwright install chromium）
 */
```

### 4.2 Report —— 同时是工具输出 schema

```js
{
  capability: 'lsp',
  ok: false,
  checks: [
    { id: 'seam', label: 'LSP seam', ok: true, detail: 'mounted', install: '' },
    { id: 'typescript', label: 'typescript-language-server', ok: false,
      detail: 'not found on PATH',
      install: 'npm install -g typescript-language-server typescript' }
  ],
  next: 'npm install -g typescript-language-server typescript'
}
```

规则：`checks` 顺序稳定；`detail` 单行、无换行；`next` 取第一个失败项的 `install`，全部通过时为空串；**所有叶子都是 string/boolean**，不用 null/数字/嵌套 union，保证 schema 落在受支持子集内。

### 4.3 引擎 API

```js
export async function runChecks(ctx, checks, options)          // → Promise<CheckResult[]>
export function defineStatusTool(capability, options)          // → ToolDefinition
export function formatReport(capabilityTitle, report)          // → string
```

- `options = { timeoutMs = 1500 }`；每个检查独立超时，超时记 `detail: 'timeout'`，不中断其他检查。
- 工具定义手写（`parameters` 是原始 JSON Schema，`output.schema` + `output.render`），**不 import `defineTool`**。

### 4.4 能力描述符

```js
export const capability = {
  id: 'lsp',
  title: { en: 'Language servers', zh: '语言服务器' },
  blastRadius: 'tool',       // 'tool' | 'session' | 'ingress'
  defaultEnabled: true,      // CI 断言：blastRadius !== 'tool' ⇒ defaultEnabled === false
  checks: [ /* Check[] */ ],
}
```

## 5. 高可用规则（逐条可测）

| 规则 | 实现 | 测试 |
|---|---|---|
| R1 探测惰性 | 只在 `execute` 时探测；`apply()` 零 IO | 单测：`apply()` 后未创建任何 promise |
| R2 有界 | 每检查 `Promise.race` + 超时 | 单测：永不 resolve 的假解析器在 100ms 预算下返回 `timeout` |
| R3 全量 catch | `runChecks` 逐项 try/catch；`execute` 外层再兜底 | 单测：抛异常的 ctx 仍返回完整报告 |
| R4 幂等 | 注册全部走 `ctx.effect(() => ctx.tools.register(...))`；模块级无状态 | 单测：disposer 调用后注册为 0 |
| R5 不写 | 不碰 `configEditor`、不写文件 | `check.mjs` 源码扫描 |
| R6 不越界 | 无 `@deepseek-ai/*` import、`dependencies` 为空 | `check.mjs` 扫描 |
| R7 降级 | 缺 seam 服务时 `ok:false, detail:'service unavailable'`，不抛 | 单测：无 `lsp` 服务的 ctx |
| R8 会话安全 | `blastRadius: 'session'` ⇒ 默认 `disabled: true` | `check.mjs` 交叉校验描述符与 patch |

## 6. 仓库结构

```
dsh-wiring/
├── .github/workflows/ci.yml        # node 24 · ubuntu + windows · 3 组命令
├── package.json                    # 单包，private，零 dependencies
├── cordis.patch.yml
├── src/
│   ├── index.js                    # 引擎 + 启动遍历
│   └── capabilities/
│       └── lsp.js                  # Step 1 唯一能力；Step 2/3 加 browser.js / webhook.js
├── test/
│   ├── engine.test.mjs             # R1/R2/R3/R4/R7 + 报告形状
│   └── lsp.test.mjs                # 描述符不变量 + 真实 schema 校验（可跳过）
├── scripts/check.mjs               # 静态验收
├── locale/{en,zh}.json
├── icon.svg
├── docs/VERIFY.md                  # 安装后 8 步可观察验收
├── SECURITY.md                     # 插件在宿主进程内运行的事实与边界
├── CONTRIBUTING.md                 # “加一个能力”的 4 步配方
├── CHANGELOG.md
├── LICENSE                         # MIT
└── README.md
```

**为什么没有 TypeScript**：包要被 profile 直接加载；编译产物会引入「源码与产物不一致」和 CI 构建步骤。用 ESM + JSDoc，`tsc --noEmit --checkJs` 只做静态检查，不产出。
**为什么是 `src/`**：不构建就不该叫 `lib/`。

## 7. 扩展配方（加一个能力）

1. `src/capabilities/<id>.js`：写 `capability`（含 `checks`）。
2. `src/index.js` 的 `capabilities` 数组加一行 import + 元素。
3. `cordis.patch.yml`：加 seam / provider / tool / 无需加 doctor 行（doctor 只有一个）。
4. `locale/{en,zh}.json` 的 `capabilities.<id>` 加标题；`test/<id>.test.mjs`；README 能力表加一行。

引擎不改。若要改引擎，说明抽象错了，先改本设计文档。

## 8. 路线图

| 步骤 | 范围 | 退出标准 |
|---|---|---|
| **Step 1（本次提示词）** | 仓库骨架 + 引擎 + LSP（仅 TypeScript 一行）+ CI + 文档 | `check.mjs` 全绿；两组单测全过；可安装且新会话出现 `lsp` 与 `lsp_status` |
| Step 2 | browser（provider 默认禁用 + 会话安全测试） | 默认安装不影响创建会话；启用后出现 `mcp__playwright-mcp__*` |
| Step 3 | webhook（适配器默认禁用 + 签名脚本） | 正确签名 202 + 新会话；错误签名 401 |
| Step 4 | TTS seam 评估 | 先做竞品与 seam 调研再决定 |

> 竞争现实：LSP 已有 `dsh-lsp-packs`（复用官方包、每语言一行）、`dsh-lsp-actions`（★39）、`satanfire/dsh-lsp`（PATH 探测）等。本项目取胜点**不是功能更多**，而是：官方包原样、零新工具面、失败可解释、默认值经得起推敲、工程可验证。README 首屏必须写清这一点，否则会被拿去比功能。

## 9. 风险

| 风险 | 触发 | 应对 |
|---|---|---|
| 官方默认发货 | LSP 三包已发 npm | 叙事放在「健康/解释」；挂载被收编后 doctor 仍成立 |
| peer 解析失败 | provider 的 peer 未满足 | VERIFY 第 2 步查 `listConfigs`；失败则 `dsh plugin add` 显式装 |
| 竞品抢跑 | 已有 5+ LSP 仓库 | 不追功能，追质量与可验证性（CI 徽章、兼容矩阵） |
| 版本漂移 | 3 个月 42 个版本 | `engines.dsh` 锁定；官方包固定版本；CI 留 allow-failure 的 next 任务 |
